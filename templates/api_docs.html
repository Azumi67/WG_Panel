Client endpoint precedence

Every code path that fills in a peer's client-facing endpoint — peer create, bulk create, config export, and the endpoint-default/apply routes below — resolves it in the same order: an explicit value on the request, then the interface's saved endpoint-default override, then auto-detection (the panel's configured domain or public IP, paired with the interface's listen port), then empty if none of those produce a value. This precedence lives in one place, resolve_client_endpoint, so nothing bypasses it.

Two fields carry endpoint data and must not be confused. Peer.endpoint is the client-facing server endpoint: the address the panel writes into the client's [Peer] block so the client knows where to dial. Peer.peer_endpoint is a fixed remote-client endpoint: written into the server's [Peer] block, and normally left empty because WireGuard learns a roaming client's endpoint from its first authenticated packet.

app.pyhandler: api_iface_endpoint_default_get
Example command
curl "https://panel.example.com/api/iface/7/endpoint-default" \
  -H "Authorization: Bearer <PANEL_API_KEY>"
What it does

Send host and port together to save the override. Sending both fields empty or null clears the override and restores auto-detection. Sending exactly one of the two fields returns 400 endpoint_partial — a partial pair is rejected so two edits made at different times can never silently merge into an endpoint nobody reviewed. endpoint_port may legitimately differ from the interface's listen_port, for example behind NAT or port forwarding. Host validation rejects whitespace, URL schemes, paths, credentials and embedded ports; port validation requires a whole number from 1 to 65535.

Returns the same payload shape as the GET route above.

What it does

Resolves the interface's effective endpoint (its saved override, or auto-detection) and writes it into Peer.endpoint for existing peers on that interface. With "dry_run": true nothing is written and the response reports would_update; a real run ("dry_run": false) writes the peers and reports updated instead. Peers that already have their own endpoint are left untouched and counted in skipped_explicit, unless overwrite_explicit is true. No endpoint to apply returns 409 endpoint_unavailable. The write is all-or-nothing: every eligible peer is updated in a single transaction, so a real run either applies to every eligible peer or changes nothing.
